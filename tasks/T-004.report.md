## 实现要点

- `src/main/window.ts`：`createWindowApi(deps, preloadAbsPath)`。**顶层只 `import type { View }`**，
  不 import `BrowserWindow` 值，单测不需要 Electron（与 T-003 `createThemeEngine` 同思路）。
- summon 的 `try/catch` 只包住 `show()`（E-WIN-011 的作用域），`t0` 在 try 之前取，
  故「t0 早于 show」在源码顺序与运行顺序上同时成立。
- `waitForRendererExit` 用**单个 resolver 槽** `exitWaiter`：`notifyRendererExit()` 由
  `window:hidden-ack` 触发并 resolve(true)；`setTimeout(ms)` 只做超时兜底 resolve(false)。
  不是 `setTimeout(ms)` 的纯 sleep。
- `flushAllPlugins` 用 `Promise.allSettled` 并发，每目标 `Promise.race([flush, delay→TIMED_OUT])`。
  超时与抛错都进 `timedOut` 桶并记 `E-WIN-012` warn（CL-219 要求调用方检查 `timedOut`）。
- `hide()` 的 `flushing = true` 在外层 `try` 之前，`finally` 里复位；flush 阶段有内层 try/catch，
  出错继续收起（E-WIN-012），但 `send` / `waitForRendererExit` 的异常**不被吞**，仍会穿过 finally 抛出。
- `getContentView(): View` 用 `as View` 收窄 `contentView: unknown`，全程无 `any`、无 `eslint-disable`。
- `src/main/ipc.ts`：`registerTestChannels` 严格只注册 `test:summon`；未满足 CL-105 时直接 return，
  不留任何 handler。

## ASSUMPTION

- **A-01**：`src/main/index.ts` 移除了原 `win.once('ready-to-show', () => win.show())`。
  按 CL-210「隐藏态（构造时）`show:false`」，显示只能经 summon()（CL-211）。影响：无（A13 实跑已验证隐藏→呼出）。
- **A-02**：`BrowserWindowLike` 在任务卡接口块之外补了**可选**成员 `destroy?(): void`。
  理由：E-WIN-011 要求「销毁旧窗口」，而 Electron `BrowserWindow.destroy()` 是既有 API，
  接口块漏列。用可选成员 + `old.destroy !== undefined` 判定，单测假窗口可自由提供或不提供。影响：无。
- **A-03**：`setChromeMetrics` 只做缓存 + 校验（有限数、非负），**不**触发真实重算；
  非法值记 warn 并丢弃。依赖插件 view（T-008）。影响：CL-217 的重算部分未覆盖，本任务卡已声明不做。
- **A-04**：`recalcAll()` 在无插件时是**空操作**（函数体只有注释）。依赖 CL-251 / T-008。
- **A-05**：`listFlushTargets()` 在生产装配处返回 `[]`（`index.ts`），本任务卡明确要求默认空实现。
  因此线上 `flushAllPlugins()` 恒返回 `{ok:[],timedOut:[]}`。
- **A-06**：`waitForRendererExit` 每次调用**覆盖**上一个 `exitWaiter`；并发两个等待者只有最后一个能收到 ack。
  理由：CL-212 是串行序列，`hide()` 不可重入；不引入队列以避免超出本卡范围。
- **A-07**：`summon()` 时若窗口已销毁（`isDestroyed()`），`ensureWindow()` 直接重建，不视为 E-WIN-011
  （E-WIN-011 针对的是 `show()` 抛错）。理由：销毁态窗口调 show 必然抛，先重建更保守。
- **A-08**：`init()` 会创建窗口但**不** show；`index.ts` 在 `whenReady` 后调用 `init()`，即构造即隐藏态。

## CONTRACT_GAP

- **G-01**：SDS CL-104 的通道表列了 `window:summon` / `window:hide`（R→M），
  但任务卡把 `registerTestChannels` 限定为「**仅**注册 `test:summon`」。
  若只按任务卡字面实现，preload 暴露的 `ark.window.summon()/hide()` 将没有 handler，A13 无法通过。
  我选择：在同一个 `ipc.ts` 里另加 `registerWindowChannels()` 与 `registerHiddenAck()`，
  与 `registerTestChannels()` 并列、互不侵入；`registerTestChannels` 本身仍严格只注册 `test:summon`
  （A12 断言 `[...handlers.keys()]` 严格相等可证）。
  理由：既满足任务卡对 `registerTestChannels` 的强约束，又满足 CL-104 的通道要求。
  影响：`ipc.ts` 的导出面比任务卡示例多两个函数。
  建议：SDS 应补一條「`ipc.ts` 按职责分函数注册（测试通道 / 窗口通道 / 单向下发）」。

- **G-02**：CL-219 规定 `waitForRendererExit` 「靠 renderer 回 `window:hidden-ack`」，
  但 CL-218 的 `WindowApi` 接口块**没有**暴露「收到 ack」的入口，
  而 `window:hidden-ack` 是 M→R 之外的 R→M 单向通道，必然由 `ipc.ts` 转交给 window 层。
  我选择：在 `WindowApi` 上补 `notifyRendererExit(): void`（内部 resolver 槽的唯一入口）。
  理由：这是让 CL-219 语义可被 IPC 层驱动的**最小**补充；不引入 EventEmitter / 回调注册表，
  避免把接口面扩大。
  影响：`WindowApi` 比 CL-218 接口块多一个成员；`waitForRendererExit` 的调用方语义不变。
  建议：SDS 在 CL-218 接口块补 `notifyRendererExit(): void  // window:hidden-ack 的落点`。

- **G-03**：CL-218 的 `getWindow(): BrowserWindow` 返回 Electron 类型，
  但任务卡要求 `createWindowApi` 可注入、单测不启动 Electron。
  两者在类型层面冲突（`BrowserWindowLike` ≠ `BrowserWindow`）。
  我选择：`WindowApi.getWindow(): BrowserWindowLike`（本卡接口块的结构化子集），
  `index.ts` 侧不做向下转换（`createMainWindow` 返回的 `BrowserWindow` 结构上兼容）。
  理由：任务卡「接口要求」的 `createWindowApi(deps, preloadAbsPath): WindowApi` 与
  「单测无需 Electron」是硬约束，优先于 CL-218 的 `BrowserWindow` 字面类型。
  影响：M-06 若需要 `BrowserWindow` 专有 API，需要在装配处自行持有 `BrowserWindow` 引用。
  建议：SDS 把 `getWindow()` 的返回类型改成结构化子集，或明确「仅本模块内部使用」。

- **G-04**：CL-212 的 hide 序列没有规定 `flushAllPlugins` **抛错**时的行为
  （CL-215 只说「超时 → warn，继续」）。
  我选择：内层 try/catch 捕获后记 `E-WIN-012` error 并**继续**收起。
  理由：与 CL-215「不阻塞用户」一致；且 A7 要求 `isFlushing` 必须复位，外层 `finally` 兜底。
  影响：A7 的「flush 抛错」用例按此实现判定。
  建议：SDS 在 CL-212 / CL-215 明确「flush 抛错等同超时：warn + 继续」。
