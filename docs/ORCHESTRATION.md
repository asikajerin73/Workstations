# 实施期调度手册（主会话跑一天不爆上下文）

## 一、上下文预算：为什么这套能跑一整天

主会话每次"看一眼"的成本，取决于它读进来多少字。

| 动作 | 朴素做法 | 本项目做法 |
|---|---|---|
| 派活 | 把需求、背景、代码全贴进 prompt | 只给文件路径 + 任务卡 ID，让子 agent 自己读 |
| 收活 | 子 agent 返回全部代码 + 全部日志 | 子 agent 只返回 ≤15 行结构化报告，细节写文件 |
| 验收 | 主会话自己 `read` 源码 | 主会话只读 `git diff --stat` + 评审 JSON 的 verdict |
| 记忆 | 靠对话历史 | 靠 `LEDGER.md` + `CONTEXT-DIGEST.md` + `DECISIONS.md` |

**一个任务在你们对话里占多少字，决定了你能跑多少任务。** 目标：每个任务在主会话里 ≤ 400 tokens。

一天 8 小时、假设 40 个任务：40 × 400 = 16k tokens，完全够。

## 二、四条硬规则

1. **主会话不读源码全文。** 需要看时只允许：
   - `git diff HEAD~1 --stat`
   - `git diff HEAD~1 -- <单文件> | Select-Object -First 120`
   - 指定的函数/行段（`read` 带 `offset`/`limit`）
2. **子 agent 报告必须结构化且短**（模板见下）。超长报告直接退回。
3. **一个任务卡只允许一个 agent 改。** 两个 agent 同改一个文件 = 你花一下午解冲突。
4. **每完成 5 个任务，压缩一次 DIGEST。** 把已完成的合并成一行，细节留在任务报告里。

## 三、任务卡（最小可执行单元）

一个任务卡 = 一个干净 agent 能独立干完的活。判断标准：

- 能在 **≤ 30 分钟 / ≤ 300 行改动** 内完成
- 只碰 **≤ 5 个文件**
- 有一条**明确的验证命令**
- 不依赖另一个未完成的任务（否则拆开或排序）

模板见 `tasks/_TEMPLATE.md`。**任务卡由主会话写，不由实施者写。**

## 四、调度循环（主会话每个 tick 做什么）

```
while 有 PENDING 任务:
    1. 读 LEDGER（只看状态列）→ 找出 READY 的任务（依赖都已 DONE）
    2. 按"文件冲突"分组：TOUCH 有交集的任务不能并行
    3. 一次并发派 2~4 个 subagent（不同文件组）
    4. 等它们回来（不是轮询，运行时会通知）
    5. 对每个完成的：
        a. 起 1 个评审 subagent（干净上下文，只给 diff + 条款号）
        b. 读评审 JSON 的 verdict
        c. PASS → LEDGER 置 DONE，追加 DIGEST 一行
           FAIL → 阻塞项回填任务卡，重派（同一任务最多 3 次）
        d. 第 3 次仍 FAIL → 升级：要么拆任务，要么回 SDS 改设计
    6. 每 5 个任务：压缩 DIGEST
```

**并发度经验值**：2~4 个。再多，冲突率和返工率上升得比吞吐快。

## 五、子 agent 派活提示词（实施）

```
你在一个多 agent 项目里担任实施者。你没有参与规划，也不需要了解全局。

开工前按顺序读：
1. AGENTS.md（项目宪法，必读）
2. tasks/T-012-add-csv-parser.md（你的任务卡）
3. docs/SDS.md 的 3.2 节与 CL-101/CL-104 条款（只读这些）
4. docs/CONTEXT-DIGEST.md 最后 30 行

规则：
- 只能修改任务卡 TOUCH 列表里的文件，越界即任务失败
- 不要修改 SDS、不要修改其他任务卡、不要改 LEDGER
- 需要新依赖必须先停下，在报告里写 DEPENDENCY_REQUEST: <理由>
- 发现 SDS 有洞：按最合理的假设继续，并在报告里写 CONTRACT_GAP: <描述>

完成后返回，且只返回这个格式（≤15 行）：
TASK: T-012
STATUS: DONE | BLOCKED
FILES: <改动的文件，一行一个>
VERIFY: <执行的验证命令> → <PASS/FAIL>（附输出最后 3 行）
ASSUMPTION: <如有>
CONTRACT_GAP: <如有>
SUMMARY: <2 句话，说明做了什么>
```

## 六、子 agent 派活提示词（评审）

见 `docs/REVIEW-PROMPTS.md` 提示词 5。要点重复一次：

- **干净上下文**（用 `subagent`，不用 `subagent_fork`）
- 只给 diff + 条款号，不给"我觉得这样写是为了..."
- 输出 JSON，`verdict` 只有 PASS/FAIL

## 七、什么时候必须停下来问人（升级清单）

| 情况 | 动作 |
|---|---|
| 同一任务失败 3 次 | 停下来：拆任务 or 改 SDS |
| 同一条款被 2 轮评审点名 | 需求问题，问人，不要继续改文字 |
| 出现 `CONTRACT_GAP` 影响 2 个以上任务 | 回 SDS 阶段补条款，不然后面全歪 |
| 需要新增外部依赖/服务 | 问人（成本与运维影响超出技术判断） |
| 验收命令开始变慢或变红 | 停下修，不要"先继续，最后一起修" |
| 任何"这个设计感觉不对"的直觉 | 记进 DECISIONS，起一个独立 agent 做对抗性评估 |

## 八、失败处理矩阵

| 失败类型 | 表现 | 处置 |
|---|---|---|
| 实现错 | 评审 FAIL，条款不符合 | 回填阻塞项，重派同一任务（不改任务卡范围） |
| 任务太大 | 子 agent 报告"做不完" | 拆成 2~3 张卡 |
| 任务太模糊 | 子 agent 反复问、假设乱猜 | 补任务卡，或回 SDS 补条款 |
| 契约冲突 | 两个任务对同一接口有不同假设 | 停下，主会话裁决并写入 DECISIONS |
| 环境问题 | 验证命令本身跑不起来 | 先修环境，任务置 BLOCKED，换下一个 READY 任务 |

## 九、一天的时间表（示例）

| 时段 | 主会话动作 | 产出 |
|---|---|---|
| 09:00-09:30 | 读 DIGEST + LEDGER，确认今日目标 5 个任务 | 今日派活清单 |
| 09:30-12:00 | 派 3 批任务 + 评审 | 8~10 个任务 DONE |
| 12:00-13:00 | 压缩 DIGEST，更新 DECISIONS | 干净的状态 |
| 13:00-17:00 | 继续派活；处理 1~2 个升级项 | 8~10 个任务 DONE |
| 17:00-17:30 | 终审 agent 跑完整验收 | 发布结论 |

## 十、LEDGER 状态机

```
PENDING → READY → IN_PROGRESS → REVIEW → DONE
                    ↓            ↓
                 BLOCKED      REJECTED → (回 IN_PROGRESS)
```

- 只有主会话能改 LEDGER
- `BLOCKED` 必须写一行原因 + 解除条件
- `REVIEW` 状态的任务不能被再次派给实施者
