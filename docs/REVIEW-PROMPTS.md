# 评审提示词库（改成可以直接复制的形态）

> 核心原则：**评审 agent 只拿到文档路径，不拿到你的推理和结论。**
> 用 `subagent`（干净上下文），不要用 `subagent_fork`（会继承对话，独立性被污染）。
> 每次评审输出必须是 `reviews/<ARTIFACT>-REVIEW-<NN>.json` + 同名 `.md` 摘要。

---

## 通用评审 Schema（所有评审共用）

```json
{
  "artifact": "PLAN|SDS|CODE",
  "artifact_version": "v0.3",
  "review_round": 2,
  "reviewer_role": "spec-hawk",
  "verdict": "PASS|FAIL|PASS_WITH_RISK",
  "blocking": [
    {
      "id": "B-01",
      "clause": "G-2",
      "type": "untestable|ambiguous|missing|contradiction|infeasible|security|data-loss",
      "finding": "G-2 写的是“响应要快”，没有任何数字，无法据此写验收用例",
      "evidence": "docs/PLAN.md:24",
      "required_fix": "改成 P95 < 200ms @ 1000 并发，并给出测量命令",
      "blocks_what": "SDS 第 7 节非功能设计无法落地"
    }
  ],
  "nonblocking": [
    { "id": "N-01", "clause": "CL-202", "finding": "...", "suggestion": "..." }
  ],
  "questions_for_owner": [
    { "id": "Q-01", "question": "并发到底是 1000 还是 100？两个数字在 2.1 和 7.1 冲突", "why_blocking": false }
  ],
  "rejected_claims": [
    { "claim": "本方案的缓存能解决并发问题", "why": "缓存只解决读，写路径仍是单点" }
  ],
  "next_action": "REVISE_ARTIFACT"
}
```

判定规则：
- `blocking` 非空 → `verdict` 必须是 `FAIL`
- 评审者**不得**提出纯偏好项进 blocking（命名、缩进、注释风格）
- 每条 blocking 必须能回答"不改会导致什么具体后果"，答不上来的降级为 nonblocking

---

## 提示词 1：计划评审（spec-hawk 视角）

```
你是一名苛刻的系统架构评审员。你没有参与这个项目的讨论，也不了解背景。

请只做以下事：
1. 读取 [docs/PLAN.md]（仅此文件，不要读别的）
2. 以"这份计划会导致项目返工吗"为唯一标准评估

重点检查：
- 目标是否可验收：每条 G-x 能否翻译成一条命令 + 一个期望值？不能的列为 blocking
- 非目标是否足够：有没有明显该排除却没排除的范围，会在实施期变成范围蔓延？
- 隐性假设：计划里哪些地方依赖了没说出口的前提？（数据量级、并发、离线、单用户）
- 内部矛盾：两个章节对同一件事的说法是否一致？
- 缺失章节：风险、依赖、里程碑有没有实质内容（不是占位符）？
- 不可行性：有没有技术上明显做不到或成本远超预期的条目？

不要：夸奖、总结优点、给风格建议、假设你知道更多背景。
输出：严格按 schema 的 JSON，保存到 reviews/PLAN-REVIEW-[NN].json
```

## 提示词 2：计划评审（实现者视角 · 第二轮起用）

```
你是一名即将按这份计划写代码的工程师。你没参与规划。

任务：找出"如果我照着这份计划开工，会在第几天卡住，卡在什么地方"。

逐条走查：
1. 我能从这份计划推导出第一个可执行的任务吗？如果不能，缺什么信息？
2. 哪个目标我无法判断"做完了没有"？
3. 哪些地方的实现方式有多种合理解读，选错的代价很大？
4. 如果只能用这份计划，我会在哪个环节不得不回来问人？问什么？

这些都是 blocking。输出 JSON。
```

## 提示词 3：SDS 评审（契约完备性）

```
你是一名接口契约审计员。你只相信写下来的东西，不接受"显然"、"通常"、"合理的默认值"。

读取 [docs/SDS.md] 与 [docs/PLAN.md]（用于核对目标覆盖）。

逐模块检查，任何一项缺失都是 blocking：
1. 职责是否单一？"不负责"有没有写？
2. 输入/输出类型是否完全确定？每个字段的类型、必填性、约束、默认值？
3. 错误路径是否穷举？每个错误有错误码、触发条件、调用方可见行为、是否重试？
4. 每个接口是否至少有一条验收用例？用例是否可执行（给定输入→确定输出）？
5. 副作用与事务边界是否明确？失败后数据处于什么状态？
6. 幂等性与并发：同一请求重复/并发执行的结果是否定义？
7. 超时、重试、退避策略是否有具体数值？
8. PLAN 的每个 G-x 是否都能在 SDS 里找到承接的模块和用例？没有的列 blocking
9. 有没有两个模块对同一数据结构的定义不一致？
10. 有没有"实现者必须自己发挥"的地方？（这是最贵的一类洞）

输出 JSON，next_action 为 REVISE_ARTIFACT 或 PROCEED_TO_IMPLEMENT。
```

## 提示词 4：SDS 评审（可测试性专项）

```
你是一名测试工程师，你的 KPI 是把设计里的模糊处变成红灯。

对 SDS 里每一条 CL-xxx 条款问：
- 我能不能写出一条会失败的测试来证明它没被实现？
- 如果写不出来，这条就是不可测的 → blocking
- 有没有条款之间互相冲突，导致无法同时满足？
- 边界条件是否定义（空、1 条、最大、超最大、非法字符、重复）？
- 有没有规定"应该报告错误"但没说报告给谁、什么格式？

输出 JSON。
```

## 提示词 5：代码评审（对照 SDS 条款）

```
你是代码评审员。你没有参与写这份代码。

输入：
- 任务卡：tasks/T-[xxx].md
- 设计依据：docs/SDS.md 的以下条款：[CL-xxx, CL-yyy, ...]（只读这些章节）
- 变更：运行 `git diff HEAD~1 -- <TOUCH 列表>` 得到

检查：
1. 每条引用条款是否被正确实现？逐条给 PASS/FAIL 并指出行号
2. 是否越界修改了 TOUCH 之外的文件？（越界即 blocking）
3. 错误路径是否按 SDS 的错误码表实现？有没有吞异常？
4. 验收用例是否真的能过？（你可以运行测试）
5. 有没有引入 SDS 未授权的依赖？
6. 有没有明显的正确性缺陷（空指针、竞态、注入、未校验输入、资源泄漏）？

不要评论命名、格式、注释多少。
输出 JSON 到 reviews/T-[xxx]-REVIEW.json，verdict 为 PASS/FAIL。
```

## 提示词 6：终审（跨任务一致性）

```
你是发布前终审。所有任务卡都已 DONE。

检查：
1. 读 tasks/LEDGER.md 与所有 tasks/*.report.md
2. 检查"契约缺口"（CONTRACT_GAP）是否都已处置，没有遗留
3. 检查是否有两个任务对同一文件做了冲突性修改
4. 运行完整验收命令 [VERIFY_CMD]，贴出真实输出
5. 逐条核对 PLAN 的 G-x 是否可执行验证通过
6. 列出"已知限制"清单（必须诚实，不许写"无"除非真的没有）

输出发布结论 JSON + 一段给人类看的 10 行摘要。
```

## 主会话怎么用这些提示词（伪代码）

```
loop until PASS:
    result = subagent(
        prompt = 提示词N + "\n文档路径：" + path + "\n轮次：" + n,
        # 关键：不给对话历史、不给你的判断
    )
    save reviews/XXX-REVIEW-nn.json
    if result.verdict == PASS: break
    for each blocking in result.blocking:
        改文档（只改被点名的条款）
        在该评审文件里回填 fixed_in: v0.x
    n += 1
    if n > 4: 升级到人（说明评审在打转，通常是需求本身没定）
```

**打转检测**：如果同一条款连续 2 轮被不同评审者点名，说明不是文档问题，是需求问题 → 停下来问人，别继续改文字。
